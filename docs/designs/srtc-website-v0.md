## Problem Statement

Saint Rambert Tennis Club (SRTC), Lyon 9e, has no website. Fabien wants a good-looking French brochure site on a custom domain, hosted on Vercel, with news, court information, address and hours, and a contact channel that reaches the club mailbox.

The second purpose is Metadot. Fabien builds Metadot apps (Tickets and KB, a customer-support product). This site is the realistic "customer site" he will later plug Metadot widgets into, to see what a normal customer goes through when installing them. In his words: "The site version 0, just have news, address, contact, court explanation… The goal after, is to plug Metadot apps with Ticket form as widgets and so on."

## What Makes This Cool

A real club with real members runs on it, so the later widget phase is a real integration test, not a demo page. The end state worth aiming for: a member opens a ticket or reads the KB from the club's own domain, in the club's own look, without ever seeing Metadot's name. v0 builds the host for that.

## Constraints

- Fully static in v0: no database, no login, no server-rendered pages. The only server code is one contact endpoint.
- Fabien is the sole editor. News posts are markdown files in the repo; publishing is a commit.
- French-language site. Real content, real club.
- Hosted on Vercel via git integration. Custom domain is part of "v0 done".
- Nothing Metadot-specific in v0. The site must look and behave like a typical small customer's site.
- Contact in v0 is email only. The Metadot ticket widget replaces it in phase 2.

## Premises (agreed)

1. v0 is fully static; pages and news are files in the repo.
2. Contact is email only; no fancy form pipeline.
3. The site looks like a typical small customer site, not a Metadot showcase.
4. Phase 2 is script-tag widgets first (ticket form, KB). API or SSO integration waits until widgets work.
5. Custom domain is part of v0 done.
6. "Pretty" means a designed site with a club identity, not a template.
7. Doing nothing costs something: Metadot has no real customer site to test on, and the club has no web presence.

## Approaches Considered

- **Astro static brochure** (minimal viable). Rejected: different framework from Metadot's Next.js apps, so nothing learned here transfers to the widget phase.
- **Next.js one-pager plus news archive** (lateral). Rejected: growth ceiling; a coaching or tariffs page breaks the one-page idea and lands back on the multi-page design.
- **Next.js on Vercel, statically generated** (ideal). Chosen. See below.

## Recommended Approach

Next.js App Router on Vercel, every page statically generated at build. Same stack as Metadot's apps, so the widget phase and any deeper integration later is home turf. With Claude the effort gap versus Astro is minutes.

### Stack

- Next.js (current stable, App Router), TypeScript, Tailwind CSS.
- `next/image` for photos, `next/font` for the two typefaces.
- Markdown news: `gray-matter` for frontmatter plus `remark` and `remark-html` for the body. No CMS, no MDX in v0.
- Contact email: Resend, called from one Route Handler. Free tier is enough for a club.
- Validation on the contact endpoint: `zod`.
- Map: a static image with a link that opens Google Maps or OpenStreetMap in a new tab. The image is either a photo of the club entrance or an OpenStreetMap render with the "© OpenStreetMap contributors" attribution. Never a Google Maps screenshot, which their terms forbid. No map iframe: a Google Maps embed sets cookies, which would force a consent banner, and it costs Lighthouse points on the home page.
- Icons: `lucide-react`, three icons, no asset pipeline.
- OG image: one static site-wide image at `public/og.jpg`, referenced through `metadataBase`. No per-post OG generation in v0.
- No analytics, no cookies, no consent banner in v0. Vercel Web Analytics is cookieless and can be added later as a one-line change if wanted.
- Do not set `output: 'export'` in the Next config. Pages are statically generated by default; the export mode would break the contact Route Handler.

### Routes

| Route | Content |
|---|---|
| `/` | Hero, three latest news, courts summary, address and hours with a map image and link, contact banner |
| `/actualites` | News archive, newest first |
| `/actualites/[slug]` | One news post |
| `/les-courts` | The courts, lighting, clubhouse, practical info |
| `/le-club` | History, bureau, how to join ("contactez-nous"). Tariffs and a membership form are post-v0 |
| `/contact` | Contact form, address, hours, map link |
| `/mentions-legales` | Required in France for any published site: publisher identity, host (Vercel), contact, and a "Données personnelles" paragraph on what the contact form collects, why, and naming Resend as the email sous-traitant |
| `/sitemap.xml`, `/robots.txt` | Generated by Next metadata routes |
| 404 | French `not-found.tsx` with a link home |

Navigation: Accueil, Actualités, Les courts, Le club, Contact. Footer: address, email, phone, socials, mentions légales. Five navigation pages plus one post template, mentions légales, and 404.

### Content model

```
content/
  site.ts                 # name, address, hours, email, phone, socials, map link
  actualites/
    2026-06-15-tournoi-interne.md
    ...
public/
  photos/                 # real club photos, Fabien supplies
```

News frontmatter: `title`, `date` (ISO), `excerpt`, optional `cover` (path under `/photos`). Slug is the filename minus `.md` and minus the leading `YYYY-MM-DD-` prefix, so `2026-06-15-tournoi-interne.md` is served at `/actualites/tournoi-interne`. Frontmatter `date` is canonical for sorting and display; the build fails if the filename has no date prefix, if the prefix disagrees with the frontmatter date, or on duplicate slugs. Posts sort by `date` descending. The home page shows up to three, fewer if fewer exist. There is no scheduled publishing: a post is live as soon as it is merged to `main`, whatever its date. Publishing a post is adding a file and pushing to `main`.

`/actualites/[slug]` uses `generateStaticParams` from the loader and `export const dynamicParams = false`, so every post is built ahead of time and an unknown slug returns the French 404 page with status 404.

`site.ts` shape: `name`, `url` (the production origin, hardcoded, used for `metadataBase`, sitemap, and OG image URLs so previews never emit preview hostnames), `address` (lines), `email`, `phone`, `socials` (label plus URL), `mapUrl`, and `hours` as a list of `{ label, value }` free-text French lines, for example `{ label: "Lundi – Vendredi", value: "8h – 22h" }`, so summer and winter schedules are just different lines.

### Contact flow

1. Form on `/contact`: nom, email, message, and a hidden honeypot field. No timing check: the pages are built once, so a rendered timestamp would be the build time, and a client-set one is forgeable. A one-line notice under the form: "Les données saisies servent uniquement à répondre à votre demande. Elles sont transmises par notre prestataire d'envoi d'e-mails (Resend) et conservées uniquement dans la boîte mail du club."
2. `POST /api/contact` Route Handler, in this order:
   - Read the honeypot first. If it is filled, return `200` and send nothing, so the bot learns nothing. The honeypot is not part of the zod schema.
   - Validate the rest with zod: `nom` 1 to 100 characters, `email` a valid address of at most 254 characters, `message` 10 to 5000 characters. Invalid input returns `400` with a French field-level message.
   - Otherwise send via Resend to `CONTACT_TO`, subject `[SRTC contact] <nom>`, `replyTo` set to the member's email so the club can answer by hitting reply.
   - Resend error: return `500`. Vercel logs carry the error; no separate alerting in v0.
3. Client shows success inline. On `400` it shows the field message. On `500` or a network failure it shows "Le formulaire n'a pas fonctionné, écrivez-nous directement à <club email>." The club email is always visible on the page as plain text.
4. Env vars on Vercel: `RESEND_API_KEY`, `CONTACT_TO`, `CONTACT_FROM`. On the preview environment `CONTACT_TO` is Fabien's own address, so test submissions never reach the club mailbox. Production gets the club mailbox.
5. `CONTACT_FROM` is an address on the club's own domain, for example `contact@<domaine>`. Resend needs that domain verified with a DKIM TXT record and an SPF record, added wherever the domain's DNS lives: the registrar, or Vercel DNS if the nameservers are moved there. Until that is done, send from Resend's onboarding sender, which only delivers to the Resend account owner's address. This means the contact success criterion cannot be met before the domain is bought.
6. Abuse ceiling: Resend's free tier is about one hundred emails a day. The honeypot covers ordinary bots. If the ceiling is ever hit, the escalation is a Vercel WAF rate-limit rule on `/api/contact`, not application code.

This form is deliberately plain. In phase 2 the Metadot ticket widget takes its place, and the Route Handler can be deleted.

### Widget readiness (phase 2 preparation, no Metadot code in v0)

- Third-party scripts go in exactly one place: the root layout, via `next/script`. Adding the Metadot snippet is a one-file change.
- No Content Security Policy in v0, so the first widget install is not blocked by headers. Adding a CSP is a phase 2 task, once the widget's origins are known.
- The contact page is built so the form block can be swapped for the ticket widget without touching the rest of the page.
- A `/aide` route is reserved (not built) for a future KB served on the club's domain.

### Deployment

- GitHub repo `fabiendv/srtc-website` connected to a Vercel project. Preview deployment per branch, production on `main`.
- Custom domain added in Vercel; the A or CNAME records Vercel instructs are added wherever the domain's DNS lives (open question 6). HTTPS is automatic.
- Env vars set in Vercel for production and preview.

## Open Questions

1. Domain name: which one, and is it already owned? If not, buy before build finishes.
2. Real club data for `content/site.ts`: street address, opening hours, contact email, phone, social links.
3. Photos: who shoots them, and when. Placeholders otherwise.
4. Mentions légales: legal name of the association, name of the président, registered address, and who to name as the contact for personal-data requests (RGPD). Required to publish the page.
5. Is SRTC affiliated to the FFT? If yes the footer can say so.
6. Where will the domain's DNS live, registrar or Vercel DNS? It decides where the Resend DKIM and SPF records and the Vercel A or CNAME records get added.

## Success Criteria

- Site live on the custom domain over HTTPS: the five navigation pages, the news post template, mentions légales, and a French 404, with real club content.
- Contact form delivers a message to the club mailbox within a minute, with the member's address as reply-to. A submission with the honeypot filled produces no email. A preview deployment never emails the club mailbox.
- An unknown news slug returns the French 404 page with status 404. No page is rendered with request-time data; the contact endpoint is the only server code.
- The home page loads no third-party iframe and sets no cookie.
- Adding a markdown file under `content/actualites` and pushing to `main` publishes a post with no other change.
- Lighthouse mobile scores of 90 or above for performance, accessibility, and SEO on the home page.
- No Metadot code anywhere; a third-party script can be added by editing one file.
- Looks like the approved mockup A on desktop and holds together on a phone.

## Distribution Plan

Web site served by Vercel. There is no pipeline yet: the repo has one commit and no Vercel project. Step 7 in Next Steps creates it. Once the GitHub repo is connected, Vercel's git integration is the whole pipeline: preview per branch, production on `main`, no CI config to write.

## Problem Statement

Saint Rambert Tennis Club (SRTC), Lyon 9e, has no website. Fabien wants a good-looking French brochure site on a custom domain, hosted on Vercel, with news, court information, address and hours, and a contact channel that reaches the club mailbox.

The second purpose is Metadot. Fabien builds Metadot apps (Tickets and KB, a customer-support product). This site is the realistic "customer site" he will later plug Metadot widgets into, to see what a normal customer goes through when installing them. In his words: "The site version 0, just have news, address, contact, court explanation… The goal after, is to plug Metadot apps with Ticket form as widgets and so on."

## What Makes This Cool

A real club with real members runs on it, so the later widget phase is a real integration test, not a demo page. The end state worth aiming for: a member opens a ticket or reads the KB from the club's own domain, in the club's own look, without ever seeing Metadot's name. v0 builds the host for that.

## Constraints

- Fully static in v0: no database, no login, no server-rendered pages. The only server code is one contact endpoint.
- Fabien is the sole editor. News posts are markdown files in the repo; publishing is a commit.
- French-language site. Real content, real club.
- Hosted on Vercel via git integration. Custom domain is part of "v0 done".
- Nothing Metadot-specific in v0. The site must look and behave like a typical small customer's site.
- Contact in v0 is email only. The Metadot ticket widget replaces it in phase 2.

## Premises (agreed)

1. v0 is fully static; pages and news are files in the repo.
2. Contact is email only; no fancy form pipeline.
3. The site looks like a typical small customer site, not a Metadot showcase.
4. Phase 2 is script-tag widgets first (ticket form, KB). API or SSO integration waits until widgets work.
5. Custom domain is part of v0 done.
6. "Pretty" means a designed site with a club identity, not a template.
7. Doing nothing costs something: Metadot has no real customer site to test on, and the club has no web presence.

## Approaches Considered

- **Astro static brochure** (minimal viable). Rejected: different framework from Metadot's Next.js apps, so nothing learned here transfers to the widget phase.
- **Next.js one-pager plus news archive** (lateral). Rejected: growth ceiling; a coaching or tariffs page breaks the one-page idea and lands back on the multi-page design.
- **Next.js on Vercel, statically generated** (ideal). Chosen. See below.

## Recommended Approach

Next.js App Router on Vercel, every page statically generated at build. Same stack as Metadot's apps, so the widget phase and any deeper integration later is home turf. With Claude the effort gap versus Astro is minutes.

### Stack

- Next.js (current stable, App Router), TypeScript, Tailwind CSS.
- `next/image` for photos, `next/font` for the two typefaces.
- Markdown news: `gray-matter` for frontmatter plus `remark` and `remark-html` for the body. No CMS, no MDX in v0.
- Contact email: Resend, called from one Route Handler. Free tier is enough for a club.
- Validation on the contact endpoint: `zod`.
- Map: a static image with a link that opens Google Maps or OpenStreetMap in a new tab. The image is either a photo of the club entrance or an OpenStreetMap render with the "© OpenStreetMap contributors" attribution. Never a Google Maps screenshot, which their terms forbid. No map iframe: a Google Maps embed sets cookies, which would force a consent banner, and it costs Lighthouse points on the home page.
- Icons: `lucide-react`, three icons, no asset pipeline.
- Tests: Vitest (dev dependency, `test` script). Unit tests cover the two non-trivial modules: the news loader's validation and sort branches, and the contact Route Handler's branches (Resend mocked). No component or E2E tests in v0.
- OG image: one static site-wide image at `public/og.jpg`, referenced through `metadataBase`. No per-post OG generation in v0.
- No analytics, no cookies, no consent banner in v0. Vercel Web Analytics is cookieless and can be added later as a one-line change if wanted.
- Do not set `output: 'export'` in the Next config. Pages are statically generated by default; the export mode would break the contact Route Handler.
- Static rendering is enforced, not assumed. Next's default is `dynamic: 'auto'`, so a later dynamic API can silently flip a page to server-rendered. Pin Next.js, the Node version (`.nvmrc` / `engines`), and the package manager (`packageManager` field + committed lockfile). Every page except the contact Route Handler sets `export const dynamic = 'force-static'`, and the build output is checked (all routes marked ○/● static, only `/api/contact` dynamic) before a deploy is called done.

### Routes

| Route | Content |
|---|---|

| `/contact` | Contact form, address, hours, map link |
| `/mentions-legales` | Required in France for any published site: publisher identity, host (Vercel), contact, and a complete "Données personnelles" section (see Privacy below) |
| `/sitemap.xml`, `/robots.txt` | Generated by Next metadata routes |
| 404 | French `not-found.tsx` with a link home |

Navigation: Accueil, Actualités, Les courts, Le club, Contact. Footer: address, email, phone, socials, mentions légales. Five navigation pages plus one post template, mentions légales, and 404.

### Content model

```
content/
  site.ts                 # name, address, hours, email, phone, socials, map link
  actualites/
    2026-06-15-tournoi-interne.md
    ...
public/
  photos/                 # real club photos, Fabien supplies
```

News frontmatter: `title`, `date` (ISO), `excerpt`, optional `cover` (path under `/photos`), optional `slug`. The slug is the explicit frontmatter `slug` when present; otherwise the filename minus `.md` and minus the leading `YYYY-MM-DD-` prefix, so `2026-06-15-tournoi-interne.md` is served at `/actualites/tournoi-interne`. The explicit `slug` exists so recurring annual events do not collide: `2026-…-tournoi-interne.md` and `2027-…-tournoi-interne.md` would both derive `tournoi-interne` and fail the duplicate-slug check, so the author sets `slug: tournoi-interne-2027` (or keeps the year in the filename). Frontmatter `date` is canonical for sorting and display; the build fails if the filename has no date prefix, if the prefix disagrees with the frontmatter date, or on duplicate slugs (post-override). Posts sort by `date` descending. The home page shows up to three, fewer if fewer exist. There is no scheduled publishing: a post is live as soon as it is merged to `main`, whatever its date. Publishing a post is adding a file and pushing to `main`.

**Single loader constraint:** exactly one module reads `content/actualites`. It validates (missing date prefix, prefix/frontmatter date mismatch, duplicate slug — build fails on any), sorts by `date` descending, and exports `getAllPosts()` and `getPostBySlug(slug)` returning typed post objects. The home page (latest three), `/actualites` (all), `/actualites/[slug]` (one), and `generateStaticParams` all consume the loader's output. No page touches the filesystem directly, so ordering and validation are identical on every path.

`/actualites/[slug]` uses `generateStaticParams` from the loader and `export const dynamicParams = false`, so every post is built ahead of time and an unknown slug returns the French 404 page with status 404.

`site.ts` shape: `name`, `url` (the production origin, hardcoded, used for `metadataBase`, sitemap, and OG image URLs so previews never emit preview hostnames), `address` (lines), `email`, `phone`, `socials` (label plus URL), `mapUrl`, and `hours` as a list of `{ label, value }` free-text French lines, for example `{ label: "Lundi – Vendredi", value: "8h – 22h" }`, so summer and winter schedules are just different lines.

### Contact flow

1. Form on `/contact`: nom, email, message, and a hidden honeypot field. No timing check: the pages are built once, so a rendered timestamp would be the build time, and a client-set one is forgeable. The form guards against accidental double-submit (disable the submit button while a request is in flight). A one-line notice under the form, truthful about where the data goes, linking to the full section in mentions légales: "Vos données (nom, e-mail, message) servent uniquement à traiter votre demande. Elles transitent par notre prestataire d'envoi Resend (conservation ~30 jours, données hébergées hors UE) puis restent dans la boîte mail du club. Détails et vos droits : Mentions légales."
2. `POST /api/contact` Route Handler, in this order:
   - Read the honeypot first. If it is filled, return `200` and send nothing, so the bot learns nothing. The honeypot is not part of the zod schema.
   - Reject an oversized body before parsing (cap the request at a few KB; the zod limits below imply a small payload, so anything larger is abuse or a malformed body and returns `400`).
   - Validate the rest with zod: `nom` 1 to 100 characters, `email` a valid address of at most 254 characters, `message` 10 to 5000 characters. Malformed/non-JSON bodies and invalid input return `400` with a French field-level message.
   - Otherwise send via Resend to `CONTACT_TO`, subject `[SRTC contact] <nom>`, `replyTo` set to the member's email so the club can answer by hitting reply. The email is **plain text only** (`text`, never `html`), so member input cannot render images, styled markup, or scripts inside the club's inbox. (Mail clients may still auto-linkify a raw URL, but nothing hidden, styled, or tracking-pixeled gets through — the class of HTML-injection risk is removed.) Before it goes in the subject, `nom` has newlines and control characters stripped (header-injection and inbox-filter safety); `message` is trimmed. No HTML template, no escaping logic to get wrong.
   - Resend error: return `500`. Vercel logs carry the error; no separate alerting in v0.
3. Client shows success inline. On `400` it shows the field message. On `500` or a network failure it shows "Le formulaire n'a pas fonctionné, écrivez-nous directement à <club email>." The club email is always visible on the page as plain text.
4. Env vars on Vercel: `RESEND_API_KEY`, `CONTACT_TO`, `CONTACT_FROM`. On the preview environment `CONTACT_TO` is Fabien's own address, so test submissions never reach the club mailbox. Production gets the club mailbox.
5. `CONTACT_TO` is the club's real mailbox — which must actually exist. The domain gives an address, not a mailbox: confirm who hosts club mail (Google Workspace, OVH, registrar mail, etc.) and provision the mailbox with recovery access before launch. **Audit the domain's existing MX, SPF, and DKIM records before touching DNS** — adding records blind can break the club's existing email.
6. `CONTACT_FROM` is a Resend-verified sender on a **dedicated sending subdomain**, for example `contact@send.<domaine>`, so Resend's DKIM/SPF live on the subdomain and cannot collide with the club's real mail on the apex. Resend needs the subdomain verified with its DKIM TXT and SPF records, added wherever the domain's DNS lives (registrar or Vercel DNS). A signed Resend DPA (sous-traitance RGPD) is on file. Until verification is done, send from Resend's onboarding sender, which only delivers to the Resend account owner's address. This means the contact success criterion cannot be met before the domain is bought and the sending subdomain verified.
7. Abuse: the honeypot covers ordinary bots, but it is trivial to bypass and Resend's free tier is only about one hundred emails a day, so a bot that fills the real fields can exhaust the quota and take the contact channel down. A Vercel WAF rate-limit rule on `/api/contact` is configured at launch (available on all Vercel plans), not deferred to escalation.
8. Failure visibility (v0-light): on a Resend error the handler logs to Vercel; a deployed smoke test (below) and Resend's own dashboard (quota, bounces) are the v0 monitoring. Owned alerting and credential rotation are captured as follow-up TODOs, not v0 code.

This form is deliberately plain. In phase 2 the Metadot ticket widget takes its place, and the Route Handler can be deleted.

### Privacy (mentions légales — "Données personnelles")

The `/mentions-legales` page carries a complete RGPD section, not a one-liner. It must state:

- **Responsable de traitement (controller):** the association SRTC, with the legal name and registered address from open question 4, and a contact for data requests (email).
- **Finalité:** répondre aux demandes envoyées via le formulaire de contact.
- **Base légale:** consentement / intérêt légitime du club à répondre.
- **Données collectées:** nom, e-mail, message. Champs obligatoires signalés.
- **Destinataires / sous-traitant:** le club, et Resend (envoi d'e-mails) — un DPA est signé. Resend conserve les données d'e-mail ~30 jours.
- **Transfert hors UE:** les données transitent par Resend (États-Unis); mention des garanties (clauses contractuelles types / DPA).
- **Durée de conservation:** ~30 jours chez Resend, puis dans la boîte mail du club le temps de traiter la demande.
- **Droits:** accès, rectification, effacement, opposition; comment les exercer (adresse de contact).
- **Réclamation:** droit de saisir la CNIL, avec le lien.

The short notice under the contact form summarizes this and links here. The two texts must stay consistent about Resend and retention.

### Visual direction

Reference mockup: variant A, editorial serif, cream and clay. Committed in the repo at `docs/designs/reference/variant-A.png` with the approval record `docs/designs/reference/approved.json`, so CI, Vercel, and future maintainers can see the reference (the private `~/.gstack/…` copy is a working artifact, not the source of truth).

- Palette drawn from the mockup: cream background, clay orange accent for headings and buttons, dark green for the footer and secondary blocks, near-black text.
- Type: Fraunces for headings, Inter for body, both via `next/font`. Revisit only if the real photos argue for something else.
- Line-art feature icons for "4 courts", "éclairage nocturne", "club-house".
- Photos carry the design. Placeholders until Fabien shoots or collects real ones. Hero is a wide shot of the courts, ideally with the Lyon hills behind.
- Hero image is the home page's LCP, so it must protect the Lighthouse mobile ≥90 target: `next/image` with `priority` (preloaded, not lazy), explicit responsive `sizes`, a blur placeholder, and a source sized to the largest rendered dimension rather than the raw camera file. `next/image` emits WebP only by default; set `images.formats` to `['image/avif','image/webp']` in the Next config for AVIF. Below-the-fold images keep the default lazy loading.
- Mobile first: the header collapses to a menu, sections stack, the map image and its link stay tappable.

### Widget readiness (phase 2 preparation, no Metadot code in v0)

- Third-party scripts mount through one reusable component (`<ThirdPartyWidgets />`), via `next/script`, rendered only on the pages that need them (`/contact` now, `/aide` later) — not the root layout, so the Metadot widget does not load site-wide. Adding the Metadot snippet is still a one-file change (edit that component), but its cost lands only on the pages that use it.
- No Content Security Policy in v0. This is deferred security work, not "readiness": the first widget install is not blocked by headers, but a CSP is a required phase 2 task once the widget's origins are known.
- The contact page is built so the form block can be swapped for the ticket widget without touching the rest of the page.
- A `/aide` route is reserved (not built) for a future KB served on the club's domain.

### Deployment

- GitHub repo `fabiendv/srtc-website` connected to a Vercel project. Preview deployment per branch, production on `main`.
- Custom domain added in Vercel; the A or CNAME records Vercel instructs are added wherever the domain's DNS lives (open question 6). HTTPS is automatic.
- Env vars set in Vercel for production and preview.

9. Infrastructure ownership: GitHub, Vercel, DNS, Resend, and the domain should be owned/billed by the association, not left as Fabien's personal accounts. Decide the ownership and a handover path.

## Success Criteria

- Site live on the custom domain over HTTPS: the five navigation pages, the news post template, mentions légales, and a French 404, with real club content.
- Contact form delivers a message to the club mailbox, with the member's address as reply-to, verified by a deployed smoke test on both preview and production (mocked unit tests do not prove real delivery, DNS auth, or preview-recipient isolation). "Within a minute" is a target observation, not an enforced SLA. A submission with the honeypot filled produces no email. A preview deployment never emails the club mailbox.
- An unknown news slug returns the French 404 page with status 404. The build output confirms every route is static except `/api/contact`; the contact endpoint is the only server code.
- The home page loads no third-party iframe and sets no cookie.
- Adding a markdown file under `content/actualites` and pushing to `main` publishes a post with no other change.
- Lighthouse mobile scores of 90 or above for performance, accessibility, and SEO on the home page.
- No Metadot code anywhere; a third-party script can be added by editing one file.
- Looks like the approved mockup A on desktop and holds together on a phone.
